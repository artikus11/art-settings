# PROJECT_STATUS.md

## 1. Исходные данные

* **Платформа/Стек:** WordPress / WooCommerce, PHP 8.x, Composer, JavaScript (jQuery, `wp-color-picker`).
* **Экосистема:** Набор кастомных плагинов с общей архитектурной базой и UI-компонентами.
* **Ключевой компонент:** Библиотека `art-settings` (подключается через VCS Composer), отвечающая за генерацию страниц
  настроек в админ-панели на основе декларативной конфигурации.
* **Базовая архитектура полей:** Класс `Field` (абстрактный базовый класс), реализующий методы передачи параметров,
  обработку атрибутов (`get_rendered_attributes()`), санитаризацию (`sanitize()`) и подключение файлов шаблонов из
  `templates/fields/*.php`.

## 2. Текущие цели этапа

* Расширить библиотеку `art-settings` штатным типом поля для выбора цвета (`ColorPicker`).
* Обеспечить автономность (self-contained) сложных полей UI, исключив их привязку к внешним скриптам в
  `SettingsManager`.
* Доработать механизм проброса кастомных HTML-атрибутов в абстракции `Field` (включая `rows`, `cols` для `Textarea`) без
  дублирования верстки в `get_rendered_attributes()`.
* Задокументировать примеры инициализации и работы новых полей для `README.md`.

* **Рефакторинг абстракции `Field`:**

## 4. Ключевые технические решения

### Автономность сложных полей UI (Self-Contained Fields)

Отказались от регистрации специфичных JS/CSS зависимостей полей в общем методе `SettingsManager::enqueue_assets()`.

* **Механизм:** Подключение штатных ассетов (`wp_enqueue_style('wp-color-picker')`,
  `wp_enqueue_script('wp-color-picker')`) происходит внутри метода `ColorPicker::render()`. Инициализация JS выполняются
  через `wp_add_inline_script('wp-color-picker', ...)` в шаблоне поля.
* **Результат:** `SettingsManager` не знает о конкретных типах полей; ресурсы загружаются исключительно на тех вкладках
  админки, где реально присутствует соответствующее поле.

### Гибкая обработка HTML-атрибутов в `Field`

Параметры, передаваемые при создании экземпляров полей, автоматически делятся на базовые свойства (`label`, `default`,
`description`, `attributes`) и произвольные атрибуты HTML-тегов (`rows`, `cols`, `placeholder` и т.д.).

```php
// Пример переопределения атрибутов при инициализации
'promo_text' => new Textarea([
    'label' => 'Текст акции',
    'rows'  => 3, // попадает в $attributes и считывается шаблоном
]);

```

Атрибуты, выводимые явно в шаблоне tag-specific образом, заносятся в массив исключений
`get_rendered_attributes(['rows', 'cols'])` для предотвращения дублирования валидации в итоговом HTML.

## 6. Результаты тестирования и проверки

* **Синтаксис и типы:** Код соответствует стандартам PHP 8.x, возвращаемые значения `sanitize_hex_color` строго
  принуждаются к типу `string` (HEX или пустая строка).
* **Изоляция ассетов:** Проверено, что на страницах настроек без колорпикера скрипты `wp-color-picker` не подключаются в
  DOM.
* **Повторный рендер:** При выводе нескольких `ColorPicker` на одной странице `wp_add_inline_script` не вызывает
  дублирования конфликтующих событий — jQuery корректно инициализирует все элементы по классу `.art-color-picker`.

---

## 7. Известные ограничения

* **Зависимость от jQuery:** Скрипт `wp-color-picker` в ядра WordPress жестко завязан на jQuery. Инициализация поля
  выполняется через `jQuery(document).ready()`.
* **Поддержка RGBA:** В текущей реализации `sanitize_hex_color()` отсекает альфа-канал (прозрачность). Если потребуется
  поддержка RGBA/HSLA, потребуется замена санитайзера и использование модифицированных палитр.

---

## 8. Опробованные, но отклоненные подходы

* **Централизованная загрузка ассетов полей в `SettingsManager`:** Отклонено. Приводит к захламлению админки ненужными
  скриптами на вкладках, где эти поля не выводятся, и требует жесткой связки `SettingsManager` со всеми классами полей.
* **Выделение отдельных JS-файлов под каждое поле в плагине:** Отклонено для простых интеграций штатных WP-компонентов.
  Использование `wp_add_inline_script` избавляет от необходимости регистрировать и хранить множество мелких `.js`
  файлов.
