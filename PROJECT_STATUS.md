# PROJECT_STATUS.md

## 1. Исходные данные

* **Контекст:** Разработка сервиса настроек в рамках библиотеки `Art\Settings` (используется плагином
  `Art\Skl\Promotion` и другими плагинами экосистемы).
* **Среда окружения:** WordPress / WooCommerce, база данных MySQL (на части сайтов используется legacy 3-байтовая
  кодировка `utf8` вместо `utf8mb4`).

## 2. Текущие цели

* Обеспечить стабильное сохранение и чтение настроек через `update_option()` без потерь данных и сбоев.
* Внедрить сервисный слой централизованной санитаризации и валидации данных на уровне библиотеки настроек (симметрично
  для сохранения и чтения).
* Сохранить совместимость со старыми базами данных (`utf8_general_ci`) без необходимости миграции структуры MySQL на
  десятках сайтов.

## 3. Завершённые задачи

* [x] Локализована проблема блокировки записи `update_option()` при отправке 4-байтовых UTF-8 символов (эмодзи) в `utf8`
  БД.
* [x] Подтверждена работоспособность механизма при очистке строковых данных от несовместимых UTF-8 последовательностей.
* [x] Разработана и протестирована концепция кодирования 4-байтовых символов в формат `\u{XXXX}` перед сохранением и
  обратного декодирования при чтении.

## 4. Ключевые технические решения

* **Слой санитаризации (`SanitizationService`):**
* В библиотеку настроек добавляется отдельный сервис `SanitizationService` (входит в модуль `Art\Settings\Services`).
* Для 4-байтовых символов Unicode (включая эмодзи) применяется обратимое кодирование через `preg_replace_callback` (
  `mb_ord` при сохранении, `mb_chr` при чтении).
* Кодирование/декодирование выполняется рекурсивно по всему массиву опций.


* **Прозрачная интеграция в репозиторий:**
* `SettingsRepository::update()` вызывает `SanitizationService::sanitize_for_save()` перед вызовом `update_option()`.
* `SettingsRepository::get()` вызывает `SanitizationService::prepare_for_read()` при получении данных из `wp_options`.
* В локальном runtime-кеше (`$this->cache`) сохраняются оригинальные декодированные строки для работы приложения без
  повторных преобразований.

## 5. Изменённые / Создаваемые файлы

* `src/Services/SanitizationService.php` *(создание)* — класс очистки, кодирования и декодирования данных.
* `src/Repositories/SettingsRepository.php` *(обновление)* — интеграция `SanitizationService` в методы `get()` и
  `update()`.

## 6. Результаты тестирования

* **Сохранение при `utf8` БД с эмодзи в тексте (например, `🔄 Восстановление доступа`):**
* *Без экранирования:* `update_option()` возвращает `false`, запись не создается и не обновляется в `wp_options`.
* *С кодированием в `\u{XXXX}`:* `update_option()` возвращает `true`, данные успешно сохраняются и читаются обратно с
  полным восстановлением исходной строки.

## 7. Опробованные, но не сработавшие подходы

* **Принудительное удаление записи перед записью (`delete_option`):** Не решило проблему, так как сбой происходил на
  этапе валидации кодировки внутри `$wpdb`, а не из-за дубликатов ключей в базе.
* **Массовая смена кодировки таблиц БД (`ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4`):** Отклонено по
  архитектурным соображениям из-за высокой трудоемкости и рисков на 30+ рабочих сайтах.

## 8. Известные проблемы

* Отсутствие единого класса для санитаризации данных перед записью в текущей версии библиотеки (санация частично была
  представлена только при чтении через геттеры типов `get_bool()`, `get_int()`).

## 9. Следующие шаги разработки

1. Создать класс `Art\Settings\Services\SanitizationService` с рекурсивной обработкой массивов и строк.
2. Внедрить `SanitizationService` в `SettingsRepository` (с поддержкой DI и дефолтного фоллбэка в конструкторе).
3. Покрыть `SanitizationService` unit-тестами на корректность экранирования/декодирования спецсимволов, эмодзи и
   вложенных массивов.
4. Обновить библиотеку `Art\Settings` и проверить интеграцию в плагине `Art\Skl\Promotion`.
